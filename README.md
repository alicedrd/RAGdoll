# RAGdoll : a simple but modular and easily extensible RAG engine.
Alice Durand (MSc 1 in AI at University Côte d'Azur)

## Goal
My goal is to create a RAG pipeline in which every part is decoupled from one another, making it highly modular, easy to extend, and not completely dependant on a few defined frameworks.

This modularity allows better experimentation and the use of systematic benchmarking to compare different technologies within each module (when I'll add metrics).

System interactions are exposed through a REST API built with FastAPI, a way that provides automated documentation (Swagger) and strict query validation (Pydantic).

## Architecture
### Core architecture
The core architecture follows the classic RAG pipeline :
- Ingesting : modular parser (adding a file format only takes a function to write)
- Chunking : uses Langchain text splitter for now, but I'm planning to rewrite it to take care of file semantics (titles, tables, etc.)
- Indexing : only ChromaDB implemented for now, but Strategy-based architecture allows for easy addition of another vector store.
- Query handling : strict payload validation through Pydantic, constraints enforcement (e. g. prompt limit)
- Context retrieval : querying vector store (e.g. ChromaDB) to collect the top k nearest chunks matching the query embedding
- Generating : link with Gemini API implemented. Again, Strategy-based architecture allowing for easy implementation of interactions with other LLM APIs.

### Interchangeability and decoupling
- As stated earlier, I tried to make pipeline component as modular as possible, by using interfaces. Implementing other technologies is as easy as writing classes that implement them.
- The engine uses two kinds of storage methods : the vector store (for embeddings) and SQL (for registry and metadata).

### Technologies used
- I'm using FastAPI and I tried to make the code as clean as possible with dependency injections (src/ragdoll/api/deps.py), Pydantic scheme validations (src/ragdoll/models/...) and centralized custom exception handling (src/ragdoll/core/exceptions.py). 
- SQLAlchemy for registry interactions.

## Installation and overview
### Prerequisites
This project uses Python 3.14 and the `uv` package manager ([installation](https://docs.astral.sh/uv/getting-started/installation/), [about uv](https://docs.astral.sh/uv/)).

To install dependencies :
```shell
$ uv sync
```

### Configuring
All settings must be centralized in a `.env` file. 

```shell
# 1. SQL registry settings
SQL_DB_URL = an URL to a SQL database (SQLite supported)

# 2. LLM API settings
LLM_PROVIDER_TYPE = "gemini" only for now. 
LLM_PROVIDER_MODEL = API model to use [Optional if use Gemini, default to Gemini 2.5 flash]
LLM_PROVIDER_API_KEY = your API key
LLM_TEMPERATURE = Temperature setting (high means creative, low means factual, so here low is better) [defaults to 0.2]

CHAT_PROMPT_LIMIT = token limit of an input prompt, to prevent excessive quota usage [defaults to 2000]

# 3. Vector store settings
RETRIEVER_TYPE = "chromadb" only for now.
RETRIEVER_DB_PATH = storage path. [defaults to "./storage/chromadb"]
RETRIEVER_COLLECTION_NAME = collection name to use in vector store [defaults to "docs"]

# 4. Chunking settings
CHUNK_SIZE = size of a context chunk [defaults to 800 characters]
CHUNK_OVERLAP = size of the piece of text repeated within two consecutive chunks of a document [defaults to 100 characters]
```

### Running
To launch the API server :
```shell
$ uv run uvicorn ragdoll.main:app
```

This will open the API on port 8000.
You can read the API specs generated by Swagger via opening `localhost:8000/docs` in your web browser.

### Quick testing with cURL
To ingest a file :
```shell
$ curl -X POST "http://localhost:8000/api/v1/documents" \
     -F "file=@my_science_paper.pdf"
```

To ask a question :
```shell
$ curl -X POST "http://localhost:8000/api/v1/chat" \
     -H "Content-Type: application/json" \
     -d '{"question": "What are the core findings of the paper?"}'
```

If an answer is found, the RAG will answer alongside the chunk sources it used. It may also say it does not know, if the question cannot be answered using documents from the DB only.

## Extending
### Adding LLM interaction supports
You can easily add suppotr for a new LLM by adding a class in `src/ragdoll/services/generator/`. 
For example, let's say you want to add the support for Claude : you would create `src/ragdoll/services/generator/claude_generator.py`. 

Your class must implement the interface `BaseGenerator` from `base_generator.py` in the same directory.

You can take a look at the class `GeminiGenerator` to make your new class compliant.
Once you have written your class, you need to edit `src/ragdoll/services/generator/__init__.py` : 
```python
from .gemini_generator import GeminiGenerator
### ADD :
from .claude_generator import ClaudeGenerator

class ProviderType(StrEnum):
    GEMINI = "gemini"
    ### ADD :
    CLAUDE = "claude"

_GENERATORS: dict[ProviderType, type[BaseGenerator]] = {
    ProviderType.GEMINI: GeminiGenerator, 
    ### ADD :
    ProviderType.CLAUDE: ClaudeGenerator
}
```
